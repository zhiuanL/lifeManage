# LifeOS — 后续扩展设计（Future Extensions）

> 本文件只描述 **V1 之后** 的扩展方向。不得把其中能力提前塞入 V1。
> 任何扩展都必须遵守最终 Life Landscape / Domain Context / Capability 架构。

# 1. 扩展设计原则

本文件只记录“现在不做，但未来可能有价值”的能力。任何扩展都必须满足两个条件：不破坏本地优先和用户主动管理原则；不显著提高日常维护成本。默认关闭、按需启用，应成为大多数高级模块的共同策略。

# 2. 高级计划与目标分析模型

| **扩展**              | **可达到的效果**                                                             | **前置条件 / 风险**                                          |
|-----------------------|------------------------------------------------------------------------------|--------------------------------------------------------------|
| 计划稳定性 / 扰动指数 | 统计原计划被修改的频率、原因、受影响目标和恢复速度，形成长期计划稳定性趋势。 | 需积累足够计划变更数据；指数只能描述模式，不能评价人生好坏。 |
| 目标推进韧性          | 衡量目标受到中断后恢复推进的时间、反复延期率、关键行动持续性。               | 需要明确区分外部中断和主动战略调整。                         |
| 跨周期目标冲突分析    | 识别多个目标长期抢占同一时间/资源、相互冲突的模式。                          | 必须避免算法把复杂价值权衡简化为单一分数。                   |
| 资源投入偏差分析      | 比较目标声明优先级与实际行动投入之间的差异。                                 | 时间/资源数据需要更完整；V1 不强制采集。                     |

# 3. 生命周期阶段管理

未来可加入“生命周期阶段”作为愿景与年度目标之间的低频战略背景，例如职业深化期、转型期、家庭建设期。记录阶段名称、时间范围、阶段重点、领域权重和结束条件。默认关闭，不要求用户强制给自己贴人生阶段标签。

# 4. 健康与可穿戴设备扩展

V1
健康只管理领域状态、目标、习惯与复盘。未来可通过插件或适配层接入手环/健康平台数据，包括睡眠、运动、心率、体重等。接口应支持“数据源—指标映射—采样时间—可信度—隐私级别”，避免把不同设备的指标直接混为同一含义。

健康数据应优先用于趋势展示和复盘背景，不自动进行医学判断。必要时只允许导出相关数据供专业工具或外部
AI 分析。

# 5. 自动数据采集与连接器

长期方向是“手动输入始终可用，自动采集成为第二输入方式并逐步承担更多事实数据”。未来可考虑日历、任务工具、阅读/学习记录、本地文件元数据、健康平台等连接器。

自动采集必须保留“来源、时间、可撤销导入、去重”机制。任何外部数据都不应直接覆盖用户手动结论。

# 6. 高级数据分析与模式发现

在积累足够长期数据后，可以增加相关性分析、滞后趋势对照、反复问题模式、领域状态与行动类型关系等高级统计。系统应明确区分“相关”“伴随变化”“规则触发”和“因果”，不得自动宣称因果关系。

复杂分析结果应配套“证据来源”视图，允许用户看到用了哪些记录、哪些时间范围、哪些指标。

# 7. 关系图谱与可视化网络

V1
只保留轻量对象关联。未来数据量足够后，可以可视化目标—领域—人物—问题—事件—能力之间的网络关系，用于回顾和导航。该功能应作为分析视图，而不是主要编辑方式，防止系统变成知识图谱工具。

# 8. 插件机制增强

V1
预留插件接口骨架，后续可加入健康数据、外部日历同步、特定职业模板、行业成长模型、数据导出器、统计分析器等。插件必须声明权限、可访问的数据对象和写入范围，默认最小权限。

# 9. 移动端与同步

桌面端 Windows 优先、架构兼容 macOS。未来手机端最适合承担“快速
Inbox、轻量状态记录、提醒、简单查看”，而不是完整配置与深度复盘。若需要跨设备同步，应优先设计可选同步层，不改变本地优先原则。

# 10. 安全能力增强

后续可加入应用密码 /
生物识别解锁、数据库加密、备份加密、敏感字段二次确认、导出脱敏预览等。由于
V1
为单人本地系统，这些暂不阻塞核心闭环，但数据库与导出格式应预留加密迁移空间。

# 11. Knowledge Hub：独立系统，而非 LifeOS 核心

电子资料、视频、图片、学习资料、笔记、软件、本地电脑/移动硬盘/网盘位置、实体物品和书籍，更适合单独的
Knowledge Hub。LifeOS
只引用这些资源，不负责存储本体，也不把文件目录管理带入人生管理主流程。

未来两者可通过资源 ID
或链接轻量关联，例如某个目标引用一门课程、某项能力引用一本书。Knowledge
Hub 可单独支持真实存储目录树、模板化批量导入导出等。

# 12. 可选的直接 AI 集成（默认不做）

当前明确原则是不直接接入 AI。未来即使技术成熟，也只建议把直接 AI
做成完全可选插件，而不是核心依赖。默认仍以“场景化上下文导出 →
用户选择任意大模型 →
用户确认”为主，确保可解释、可迁移、不过度依赖单一模型。

# 13. 扩展优先级判断标准

任何后续扩展上线前，应回答三个问题：它是否显著提高“看清状态、目标—行动一致、规律复盘、重大决策依据、早发现问题”中的至少一项？它是否能把日常额外维护控制在很低水平？如果关闭它，LifeOS
核心闭环是否仍完整？只有前两项答案为“是”、第三项为“是”，才适合作为扩展而不是核心依赖。
